## 1. Objetivo de la jornada

Arrancar el **Paso 2** del plan (el *merge*): construir la aplicación React sobre la base de
datos ya desplegada — shell único, autenticación real y acceso por rol. En paralelo,
**endurecer el modelo de niveles de rol** en la base de datos.

Recordatorio de los tres pasos: **1) SQL** (base de datos, completado el 2026-06-06) ·
**2) Merge** (core de la app, foco de hoy) · **3) Visual** (pulido de identidad, último).

---

## 2. Decisiones de arquitectura tomadas

- **Lenguaje: TypeScript.** Se eligió TS sobre JavaScript por el type-safety contra el schema
  (caza typos de columnas antes de correr), asumiendo la curva de aprendizaje a cambio de
  robustez para una app clínica.
- **Reusar el design system existente** ("Identidad Visual / Sereno"): tokens CSS, shell,
  isotipo (vilano) e íconos se portaron a TypeScript siguiendo el `HANDOFF.md` — no se reinventó.
- **Seguridad del front:** producción **sin sourcemaps**; la *Publishable key* es pública (la
  protege la RLS); la *service_role* nunca toca el front; el `.env` queda fuera del repo.
- **Modelo de niveles de rol** (escalera `viewer < operator < leader < admin`, por módulo):
  viewer solo lectura; operator opera y configura su módulo; leader + el catálogo de medicación
  (pharma); gerencia administra roles, auditoría y borrados. *Carve-out* de seguridad: asignar
  coordinadores a protocolos queda en leader (control de acceso, no operator).

## 3. Trabajo realizado

### 3.1 Scaffold del front
Proyecto **Vite + React 19 + TypeScript** en la raíz del repo, con `build.sourcemap = false`.
Build verificado (tsc + vite).

### 3.2 Design system y shell en TypeScript
Se portaron desde el prototipo: tokens CSS (tema claro/oscuro vía `[data-theme]` +
`localStorage`), componentes `Icon` y `Vilano` (isotipo de marca), el registro de
módulos/submódulos, y el **AppShell** (barra superior + riel de módulos + panel de submódulos +
navegación de dos niveles + gating visual).

### 3.3 Integración Supabase: login real y acceso por rol
Cliente Supabase, `AuthProvider` (sesión + perfil de `public.users` + roles de
`user_module_roles`), pantalla de **login real** (email/contraseña), y **gating de módulos según
el rol real** del usuario — reemplaza el `allowed` hardcodeado del prototipo.

### 3.4 Migración 0009 — niveles de rol estrictos
Helpers `role_rank` + `has_min_role` (la escalera de niveles) y ajuste de todas las policies de
escritura para que cada nivel no pueda pasarse del suyo (un viewer no escribe; el catálogo de
medicación es solo de la farmacéutica; etc.).

## 5. Problemas encontrados y resueltos (para referencia futura)

| Problema | Causa | Solución |
|---|---|---|
| `permission denied for table auth.users` (en el test de RLS) | el rol `authenticated` no puede leer el schema `auth` (protegido a propósito) | usar `auth.uid()` (lee el token), no consultar `auth.users` |
| Verificación con ruta inválida en `node -e` al instalar | path estilo git-bash no válido para `require` de Node | trivial — la instalación fue correcta igual; ajustar la verificación |
