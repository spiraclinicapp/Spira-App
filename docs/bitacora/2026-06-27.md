## 3. Portabilidad (decisión de diseño)

El usuario quiere poder reutilizar el módulo Pharma en otros sistemas. Conclusión, con base en cómo está el repo: **la capa de datos depende SOLO de primitivas del Core** (`lib/supabase` + `lib/useSupabaseQuery`); el acoplamiento real es el **schema** (FK a `protocols`/`users`/`patient_visits` + RBAC/audit del Core). Estrategia adoptada: **co-localizar el módulo** (`src/data/pharma/`, `src/views/pharma/`), importar solo primitivas del Core (nunca de Track), y documentar el **"Contrato del Core"** (checklist de portabilidad) en el plan de la capa de datos. No es drop-in: es modular sobre el Core, por diseño.

## 4. Vista Medicamentos — `pharma/medicamentos` (commit `709fce3`)

Selector de protocolo + lista de stock (`v_medication_stock`) con badges (sin stock / bajo / en stock) + 3 modales: **alta de medicamento** global (con alta de droga inline + GTIN + "asignar a este protocolo"), **asignar** un medicamento del catálogo, y **ajustar stock** por lote (motivo desplegable). Todo por desplegables (protocolo / unidad / droga / lote / motivo / filtro); texto libre solo en nombre/GTIN/nota/buscador (principio del Director).

---

## 5. Vista Recepción — `pharma/recepcion` (commit `f84d420`)

Cola espejo de "Visitas del día": recepciones por protocolo (fecha, estado **pendiente/verificada** en color, renglones con nombre de medicamento) + botón **Verificar** (`verify_reception` → el trigger ingresa el stock). Modal **Nueva recepción**: fecha + notas + constructor de renglones (medicamento asignado por desplegable + lote + vencimiento + cantidad) y un **escáner** que precarga los medicamentos de códigos conocidos (auto-asigna al protocolo si hace falta). **Diferido:** guardado on-demand de códigos NUEVOS (`linkCode`).
